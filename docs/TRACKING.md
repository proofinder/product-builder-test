# 트래킹 방식 선택 — 무엇을 재보고 무엇을 골랐는가

"KLT를 꼭 쓸 필요는 없다"는 지침에 따라 대안들을 검토했습니다. 결론부터:

| 후보 | 판정 | 근거 |
|---|---|---|
| KLT (레퍼런스) | **미채택** | iOS에 공개 API 없음 |
| **Vision 랜드마크 + similarity 피팅** | **채택** | 대응이 이미 잡힌 서브픽셀 점 집합, 전 기종 지원, 카메라 완전 제어 |
| IRLS(Tukey) 강건 피팅 | **미채택** | 시뮬레이션 결과 **이득 없음** (아래) |
| 코너 대신 랜드마크 중심 사용 | **미채택** | 1.15배뿐, 사양(코너 4개 평균 y)을 벗어날 값어치 없음 |
| ARKit `ARFaceAnchor` | **보류** | 자세 추정은 최고. 다만 TrueDepth 필요(iPad Pro 한정) |
| 랜드마크 개수 늘리기 | **채택, 설정으로 노출** | **2배 개선** — 실제로 유일하게 유의미한 지렛대 |

---

## 1. 왜 KLT가 아닌가

`rPPG_test.m`은 `detectMinEigenFeatures` + `vision.PointTracker`(KLT)로 특징점을 추적하고
`estgeotform2d`로 similarity 변환을 구해 박스 코너에 적용합니다. **구조는 그대로 따르되**,
iOS에 KLT가 공개 API로 없으므로 특징점 공급원만 바꿨습니다.

Vision 얼굴 랜드마크가 KLT보다 나은 점:

- **대응이 공짜** — KLT는 점을 추적해야 대응이 생기고, 놓치면 재초기화가 필요합니다.
  랜드마크는 매 프레임 같은 의미의 점이 같은 순서로 나옵니다.
- **드리프트 없음** — KLT는 프레임 간 누적이라 서서히 밀립니다. 랜드마크는 매번 절대 위치입니다.
- **재획득이 공짜** — 얼굴이 잠깐 사라졌다 돌아와도 그냥 다시 검출됩니다.

여기에 더해 **이전 프레임이 아니라 최초 앵커에 대해** 피팅합니다. 프레임 간 변환을 누적하면
드리프트가 쌓이는데, **코너 y의 느린 드리프트는 호흡과 구분되지 않습니다.**

## 2. IRLS(Tukey biweight) — 재보고 버렸습니다

가설: 하드 프루닝은 이상치가 임계 근처에서 오락가락할 때 인라이어 집합이 깜빡이고,
그때마다 피팅된 변환이 계단처럼 튄다. 소프트 가중치(IRLS)면 그 불연속이 사라진다.

측정: 랜드마크 하나를 임계 부근에서 진동시키고(±9 px), 나머지에 1 px 잡음을 준 뒤
400 tick 동안 **tick 간 코너 이동량**을 비교.

```
hard-prune   tick-to-tick corner step: mean 0.5800 px   max 1.6281 px
IRLS-Tukey   tick-to-tick corner step: mean 0.5788 px   max 1.6371 px
```

**차이 없음.** 잡음이 깜빡임보다 훨씬 크기 때문입니다. 정확도·이상치 배제도 동일했습니다
(알려진 변환 1e-14 복원, 주입한 이상치 정확히 배제).

코드만 복잡해지므로 채택하지 않았습니다. 현재의 하드 프루닝은
`estgeotform2d`의 `MaxDistance` 의미도 그대로 유지합니다.

> 다만 임계값은 그냥 4 px 고정이 아니라 `max(4 px, 2.5 × median residual)` 입니다.
> 고정 임계만 쓰면 이상치가 첫 피팅을 끌어당겼을 때 **모든** 점의 잔차가 임계를 넘어
> 전부 제거되고 피팅할 게 없어집니다. 테스트로 고정해 두었습니다.

## 3. 코너 대신 랜드마크 중심? — 1.15배뿐

사양은 "코너 4개 좌표의 평균 y"입니다. 직사각형에서 그건 quad 중심의 y이고,
similarity 변환에서 quad 중심은 `T(앵커 quad 중심)` 입니다. 앵커 quad 중심이 랜드마크 중심과
어긋난 만큼(lever arm) 회전·스케일 잡음이 증폭됩니다.

측정 (220×280 박스, 랜드마크 축당 잡음 1.5 px):

```
n=20  lever=36.0 px | meanCornerY std 0.389 px | 랜드마크 중심 y std 0.329 px | 1.18배
n=40  lever=32.0 px | meanCornerY std 0.273 px | 랜드마크 중심 y std 0.235 px | 1.16배
n=76  lever=29.5 px | meanCornerY std 0.199 px | 랜드마크 중심 y std 0.174 px | 1.14배
```

**1.15배 남짓**입니다. 사양에서 벗어날 만한 값어치가 아니므로 코너 평균 y를 그대로 씁니다.

## 4. 실제 지렛대는 랜드마크 개수 — 2배

같은 표를 세로로 보면 답이 나옵니다.

```
20 points  0.39 px
40 points  0.27 px
76 points  0.20 px
```

피팅이 독립 잡음을 `√개수` 로 줄이기 때문입니다. **호흡에 의한 머리 상하 움직임이
태블릿 거리에서 대략 0.5–2 px**이므로, 0.39 px과 0.20 px은 "신호가 잡음에 묻히느냐"의 차이입니다.

문제는 늘어나는 점이 **가장 덜 rigid한 점들**이라는 것입니다.

- 입(`outerLips`) — 말하거나 표정을 지으면 움직임
- 얼굴 외곽선(`faceContour`) — 고개를 돌리면 머리 위를 미끄러짐 (yaw가 피팅에 새어 들어감)

정지·무언 상태에서는 다 넣는 게 유리하고, 말하거나 움직이면 불리합니다. **이건 이론으로
정할 문제가 아니라 재볼 문제**라서 UI 설정으로 뺐습니다.

### 재보는 법

Tracking 패널 맨 아래 **Landmarks** 선택기: `Rigid` / `＋Mouth` / `All`.
바꾸면 재앵커링되고 측정 창이 초기화됩니다. 각각에 대해:

1. 프리셋 선택 (자동으로 stats 초기화됨)
2. 1분 정지
3. **Corner jitter** 수치 기록

실제 사용 조건(가만히 있을지, 말할지)에서 가장 낮은 것을 고르면 됩니다.

## 5. ARKit — 보류한 이유

`ARFaceTrackingConfiguration` + `ARFaceAnchor.transform` 은 iOS에서 얻을 수 있는
가장 정확한 머리 자세입니다 (6DoF, 60 Hz, TrueDepth 깊이 기반).

보류한 이유:

- **TrueDepth가 필요합니다.** Face ID가 있는 iPad Pro만 됩니다. iPad Air / iPad mini /
  일반 iPad는 안 됩니다. 대상 기기가 정해지지 않은 상태에서 기종을 좁히게 됩니다.
- **카메라 제어권.** rPPG는 노출·화이트밸런스 고정이 생명인데 ARKit이 세션을 소유합니다.
  iOS 16의 `ARConfiguration.configurableCaptureDeviceForPrimaryCamera` 로 잠글 수 있을
  것으로 보이지만, 이 환경에서 검증할 수 없었습니다.
- 현재 방식으로 코너 지터가 기준(얼굴 폭 0.5 %)을 통과하면 **바꿀 이유가 없습니다.**

**판단 순서:** 먼저 Stage 2의 corner jitter를 세 프리셋으로 재보고, 그래도 기준을 못 넘기면
그때 대상 기기가 iPad Pro인지 확인한 뒤 ARKit 경로를 붙이는 게 맞습니다.
